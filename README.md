# DSH ↔ Telegram: один бот, несколько шлюзов

Плагин для **DSH 0.2.2-rc.1**, Node.js **22.19+**. Центральный процесс получает Telegram updates; каждый Harness подключается к нему исходящими HTTPS-запросами. SQLite входит в Node.js; ответы Markdown разбираются `markdown-it` 14.1.0, зависимости закреплены в npm-shrinkwrap.json.

## Поведение

- Один бот, личный чат только с заданным числовым `ownerId`, отдельная тема для каждой обычной конверсации. Тема содержит метку шлюза. Пустые сессии Harness не создают тем до первого сообщения; уже существующие темы не удаляются из-за пустого состояния. Созданная пользователем Telegram-тема привязывается сразу после подтверждения создания сессии.
- В Telegram видны конверсации обоих шлюзов. Ключ — пара `gatewayId + sessionId`, поэтому одинаковые UUID на разных машинах не смешиваются. Задача всегда исполняется на машине создания конверсации. Это **не клонирование журналов сессий между двумя установками DSH**: единое представление переписки находится в Telegram; рабочие проекты и секреты не копируются.
- При первом подключении существующих конверсаций запоминается текущая граница истории. Старые сообщения не отправляются; для новых конверсаций передаётся и первое сообщение. Дальнейшие сообщения, поступившие во время перерыва связи, догружаются по сохранённому курсору.
- Текст, сохранённые в сообщениях DSH изображения и файлы, входящие Telegram-фото, документы, голосовые, аудио и видео. Голосовое поступает в DSH как файл: автоматическая расшифровка не реализована. Альбомы поступают отдельными сообщениями, объединение альбома в один запрос не реализовано.
- Markdown ответов ассистента преобразуется в Telegram entities: жирный, курсив, зачёркивание, ссылки, inline-код и блоки кода с языком. Та же обработка применяется к редактированию. Длинные сообщения делятся после разбора с пересчётом UTF-16 offsets; emoji не разрезаются. HTML не исполняется; сообщения пользователя и служебные условия не интерпретируются как Markdown.
- Реакция «глаза» ставится после сохранения текста/байтов вложения в долговременную очередь. Это не подтверждение выполнения. При получении сообщения в связанной теме `typing` отправляется сразу, если машина имеет свежий heartbeat; затем обновляется каждые четыре секунды по текущему статусу `running` Harness. После потери heartbeat прекращается.
- Пустые события инструментов не занимают очередь переписки. При накоплении сообщений шлюз передаёт до 100 событий за обмен и продолжает без дополнительной двухсекундной паузы, только если есть подтверждённый прогресс. Новый запрос подтверждения ждёт передачи предшествующего контекста своей сессии; relay ставит карточку после текста и не пропускает её вперёд при ошибке или повторе отправки текста.
- Вопросы Harness приходят кнопками: одиночный и множественный выбор, «Готово», «Пропустить», страницы вариантов. Для обычного вопроса можно написать свой ответ в теме. У вопросов с intent подтверждения нет пропуска и произвольного текста. Состояние выбора сохраняется при перезапуске relay. Вопросы, продолженные после тайм-аута, восстанавливаются из проекции DSH; ответ поступает через штатный `userQuestions.answer`.
- Подтверждения инструментов, включая Auto review и повышение прав sandbox, предлагают только «Разрешить один раз» и «Отклонить», без изменения глобальной политики. Локализованная причина преобразуется в русский текст с резервным английским/исходным пояснением. Условия отправляются полностью до кнопок. Проверяются пользователь, чат, тема, конкретное сообщение, nonce и версия карточки; устаревшая кнопка не может разрешить другой запрос. Ответ в GUI Harness закрывает карточку Telegram. При отсутствии свежего heartbeat ответ кнопкой отклоняется, а не сохраняется как будущее разрешение.
- Инструмент `telegram_sync_return_file` подготавливает существующий файл или созданное изображение. Чтение идёт через составной `ctx.fs`, со снимком байтов, проверкой версии и лимита. Публикация требует успешного конечного `tools/result`, включая всех родителей Code Mode, и `turn/end` с причиной `completed`. Отменённый/ошибочный ход не отправляет файл. Изображения этим инструментом отправляются документами, без изменения исходных байтов.
- Архивирование из Harness **удаляет Telegram-тему вместе с историей**, как выбрано пользователем. Восстановление создаёт новую пустую тему. Старые очереди сообщений из предыдущего поколения темы не воспроизводятся. Нативное закрытие темы в личке не используется.
- Исчезновение из успешного **полного** списка `sessionQuery` удаляет тему. Ошибка запроса, отключение машины или `session/disposed` не считаются удалением. В исследованном DSH нет публичного API удаления конверсации; удаление файлов журналов этот плагин не выполняет.
- Архивирование и восстановление идут только из Harness; создание также доступно выбором машины внутри Telegram-темы. Ручные удаления в Telegram обратно в DSH не передаются; удалённая вручную тема автоматически не воссоздаётся.
- Редактирование входящего текста меняет ещё ожидающий элемент очереди DSH. Если сообщение уже принято в историю или содержит вложение, приходит отдельное явно обозначенное исправление с собственным requestId. У DSH нет API перезаписи уже принятого сообщения. Одно текстовое замещение из DSH редактирует известное сообщение бота; сложное замещение передаётся отдельным исправлением.

## Границы текущей реализации

Плагин передаёт переписку, кнопочные вопросы/подтверждения и файлы. Локальные файлы, которые агент лишь создал или упомянул ссылкой, не рассылаются автоматически: агент должен вызвать `telegram_sync_return_file`; инструкция об этом добавляется в контекст Harness. Инструмент другого IM-плагина `dsh_im_return_file` не перехватывается. Контакты, геопозиции, опросы и прочие не перечисленные выше типы не преобразуются в задачи. Новую привязанную конверсацию можно создать в Harness либо создать тему в Telegram и выбрать Mac/VPS внутри неё. Без явного выбора машины непривязанная тема сессию не запускает.

Лимит моста — 20 MiB вложений на сообщение. Он выбран под облачный Telegram `getFile`; более крупный объект сохраняет непройденный курсор на шлюзе и требует вмешательства, а не молча теряется. Крупные или неподходящие по геометрии картинки отправляются документами. Бот не платит Telegram Stars, не включает paid broadcast.

## Новый диалог из Telegram

Основной поток в relay 0.1.7+: создайте тему штатной кнопкой Telegram. В этой же теме бот предлагает Mac/VPS; после выбора создаёт Session на выбранном Host и привязывает **эту же** тему, без дополнительной темы, перехода и обязательных скобок. Если клиент не прислал service event создания, первое сообщение в непривязанной теме также открывает выбор. Сообщения до выбора/подтверждения хранятся в durable held-состоянии и после привязки отправляются только выбранному Host; до выбора модель не запускается.

В relay 0.1.9+ запасная кнопка «Новый диалог» убрана. После выбора карточка Mac/VPS заменяется единственным коротким «Подключено к Mac/VPS.» без кнопок и второго welcome-сообщения. Старые кнопки и команды показывают только инструкцию создания штатной темы, а не создают дополнительные сессии. Startup не публикует глобальное меню и не редактирует историю. Старые уже отправленные сообщения сохраняются. Выбор Mac/VPS привязан к owner, private chat, конкретному сообщению и теме, действует 30 минут и создаёт только один запрос.

Для создания нужны Gateway 0.1.6+ с capability `session-create-v1`. Старый или выключенный Host не получает неподдерживаемую команду; запрос ждёт именно выбранную машину без failover. Рабочий каталог берётся из `newSessionCwd` в конфигурации Gateway либо `ctx.workingDirectory.defaultDirectory` этого Host; корень файловой системы как неявный workspace запрещён. Модель и preset наследуются штатным способом; `selectModel` не вызывается и global default не меняется.

Стабильный UUID и durable phase marker сохраняются до native create. После сбоя сначала проверяется существующая identity: `session.create` **не** является exactly-once API и при повторном использовании уже начатой сессии способен вернуть другую. Такой результат не привязывается молча. Успех подтверждается только после flush точной Session; неизвестный исход требует сверки, а не повторного create. GUI-переименования при recovery не перезаписываются. Меню показывает готовность только после ACK и получения topic binding. Потеря callback ACK не повторяет бизнес-действие; неизвестный исход отправки карточки не повторяется фоновым refresh. Исторические сообщения и persistent menu carrier не удаляются.

## Звук уведомлений

В relay-конфигурации `notifications.silentMessages: true` делает обычную переписку, файлы и изображения тихими (`disable_notification=true`). `questions: true` оставляет звук первой карточке вопроса/подтверждения; её длинные условия приходят тихо. `completion: true` оставляет обычное уведомление самому итоговому ответу, когда ответ и завершение хода пришли в одном пакете; отдельное «Задача завершена» не отправляется. Длинный итоговый ответ уведомляет только первым фрагментом. Если завершение пришло позже уже отправленного ответа или итог обновлён редактированием, дополнительного уведомления нет. Ошибки и блокировки по-прежнему приходят отдельным важным сообщением. Нужны шлюзы 0.1.4+ (`notifyTurns` включён по умолчанию). Старые завершения не догружаются.

`mentions: true` оставляет звук явному @username владельца и ссылке `tg://user?id=<ownerId>`. Username читается через `getChat` при старте и кешируется; код, чужие ссылки и похожие имена не считаются пингом. Первое появление упоминания при редактировании вызывает отдельный звуковой пинг, поскольку само редактирование Telegram не уведомляет. По умолчанию тихий режим, завершения и упоминания выключены, вопросы звучат как прежде. Уведомления уважают ручной мьют чата и настройки телефона; бот не может их обойти. Тихие сообщения всё равно могут показывать уведомления без звука.

## Надёжность и доступ

Состояние и очереди хранятся в SQLite с WAL и `synchronous=FULL`, база создаётся с правами `0600`. Базы содержат переписку и вложения; файловая система и резервные копии должны защищать их как пользовательские данные. На уровне приложения шифрования содержимого нет.

Telegram offset продвигается атомарно с записью updates. События DSH дедуплицируются по шлюзу, сессии и seq; входящие prompts используют стабильный `requestId`. Подтверждение принятого prompt и позднего ответа на продолженный вопрос формируется после flush журнала; ответ на живой waterfall-запрос возвращается его штатному владельцу, который записывает результат. Файловый снимок долговременно хранится в SQLite в состоянии `held` до наблюдения завершённого хода. Для восстановления после сбоя шлюз повторно передаёт сырые события истории файловому наблюдателю; это не обещание общей атомарной транзакции между журналом DSH и SQLite. Очередь недоступной машины остаётся на центральном процессе и не передаётся другой машине. Для каждого шлюза нужен отдельный длинный токен. HTTP разрешён только на loopback; удалённые соединения требуют HTTPS. Не запускайте две копии одного gatewayId и не удаляйте его SQLite: счётчик ревизий и границы истории являются частью идентичности шлюза.

Потеря ответа на Telegram `sendMessage`/`createForumTopic` не позволяет доказать, было ли действие выполнено. Такие задания переходят в `uncertain`, в том числе после перезапуска с незавершённым `sending`, и **не повторяются автоматически**. Зависимые действия ждут восстановления известной темы, остальные конверсации продолжают работать. Ошибка 429 сохраняет задание с указанной Telegram задержкой. Успешно отправленные части большого текста имеют отдельные сохранённые receipts. Это не гарантия exactly-once между Telegram и SQLite. Для `failed`/`uncertain` требуется сверить Telegram и базу; автоматического инструмента принятия решения сейчас нет.

Ошибки не содержат токены, полные URL Telegram, текст сообщений и содержимое файлов. Для первой проверки используйте отдельного тестового бота/тему. Не подключайте токен одновременно к этому приёмнику и существующему IM-плагину.

## Настройка центрального процесса

Пример конфигурации: [config.example.json](config.example.json). Скопируйте его в закрытый каталог, задайте реальный `ownerId`, путь базы и имена переменных окружения. Значения токенов в JSON не нужны.

1. В BotFather включите режим тем в личном чате. При запуске проверяется `getMe.has_topics_enabled`.
2. Остановите **только обработчик этого бота** в прежнем IM-плагине и убедитесь, что другой long-polling consumer не работает. Webhook не сбрасывается автоматически; наличие webhook блокирует запуск.
3. После согласованного переключения задайте `exclusiveBotConfirmed: true`. По умолчанию пример отказывается запускаться, чтобы случайно не перехватить текущего бота.
4. Передайте через защищённое окружение `TELEGRAM_BOT_TOKEN`, `DSH_SYNC_LOCAL_TOKEN`, `DSH_SYNC_SERVER_TOKEN`. Токены шлюзов должны быть различными и не короче 32 символов.
5. Запустите из каталога пакета:

```sh
npm ci --ignore-scripts --omit=dev
node bin/relay.mjs /absolute/path/to/config.json
```

Центральный процесс по умолчанию слушает `127.0.0.1:8791`. Для удалённых шлюзов нужен согласованный HTTPS reverse proxy; его установка, сертификаты, автозапуск, открытие портов и deploy не выполняются этим пакетом. SQLite должен находиться на локальном диске, не в синхронизируемой сетевой папке. Один центральный процесс на бота; lease в одной базе защищает от второго запуска с той же базой, но не обнаруживает посторонний процесс с другой базой.

## Настройка каждого Harness

Соберите пакет из этого репозитория:

```sh
git clone https://github.com/the-evgenii/dsh-telegram-sync.git
cd dsh-telegram-sync
npm ci --ignore-scripts
npm pack --ignore-scripts
```

Установите полученный `dsh-telegram-sync-<version>.tgz` как DSH bundle через штатный plugin manager. Пакет не публиковался в npm registry. Bundle добавляет отключённую запись `telegram-conversation-sync`, поэтому одна установка ничего не переключает.

В patch соответствующего профиля переопределите запись:

```yaml
- id: telegram-conversation-sync
  disabled: false
  config:
    relayUrl: https://your-relay.example
    gatewayId: local
    statePath: /absolute/private/path/local.sqlite
    newSessionCwd: /absolute/path/to/workspace
```

Токен передаётся процессу Harness как `DSH_TELEGRAM_GATEWAY_TOKEN` либо защищённым `config.gatewayToken`. На сервере используются `gatewayId: server`, собственная база и другой токен. Учтите, что переменные оболочки не появляются автоматически в уже работающем macOS-приложении. В зависимости от HMR профиля может требоваться перезапуск; пакет не перезапускает приложение сам. Стандартный sandbox/approval режим DSH не меняется.

Перед реальным переключением: проверить версию DSH на обеих машинах, сохранить резервные копии конфигов, подтвердить единственный Telegram consumer и доступ к relay из обоих Harness, затем проверить сообщение, вложение, офлайн-очередь, архив и восстановление на тестовой конверсации. Не проверяйте удаление на ценной переписке.

## Проверки разработки

```sh
node scripts/check.mjs
```

Проверяются синтаксис всех модулей и тесты на `node:test` без дополнительных зависимостей. Тесты используют настоящие временные SQLite-базы и локальные HTTP-серверы для Telegram/relay. Они проверяют polling/offset, авторизацию, два шлюза, сохранение очередей, архив/восстановление, поздние receipts, ошибки отправки/удаления, 429, uncertain, пагинацию истории, отсутствие эха, передачу байтов, редактирование, весь HTTP-путь кнопка → relay → шлюз → ответ Harness, гонку с GUI, поздние вопросы, публикацию файлов после успешного tools/result/хода, Code Mode, отмену, изменение файла и лимит размера. Они **не доказывают live-работу в клиенте Telegram, на удалённом сервере или в установленном Cordis-профиле**.
